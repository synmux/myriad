How a GPU Works

Thousands of simple cores that trade latency for throughput

sourceNVIDIA H100 datasheet, AMD EPYC 9654 spec sheet, Perplexity research 2026-10-24

A GPU wins when one instruction applies to many data items at once. It gives up branch prediction, big caches and high clocks, and spends the transistors on arithmetic units instead.

A

The one-line answer

Throughput, not latency

A CPU makes one thread finish fast. A GPU makes tens of thousands of threads finish together.

It hides memory waits mainly by switching to another ready group of threads, not by speculating on one thread's future. If your problem is the same maths on a large array, a GPU is the right tool. If it is a long chain of dependent decisions, it is not.

The CPU has 8 times the cache. The GPU has 7 times the memory bandwidth and about 10 times the raw FP32 arithmetic. A CUDA core is one arithmetic lane. It does not fetch or schedule its own instructions, so 16896 against 96 is not a like-for-like count. The CPU FP32 figure is a theoretical estimate from core count and vector width, not an AMD-published number.

One SM is roughly one CPU core in area. The CPU core spends that area on out-of-order logic, branch predictors and a private L2. The SM spends it on 128 arithmetic logic units (ALUs) and a register file eight times larger than a CPU core's.

D

Execution: one instruction, 32 threads

This model is called single instruction, multiple threads (SIMT). The scheduler issues one instruction, and 32 lanes run it on 32 data items. A warp is NVIDIA's name for the group of threads scheduled together, and it is 32 wide. AMD calls the group a wavefront: RDNA uses 32 or 64 (wave32, wave64) and CDNA uses 64.

When threads in one warp take different branches, the hardware runs both paths with the idle lanes masked off. A 50/50 split leaves half the lanes idle on each path, so that region takes about twice as long. Different warps diverge independently at no cost. Since Volta, NVIDIA tracks per-thread state so sub-warp paths can interleave, but the lanes still share one issue slot. Branchy code is where GPUs lose.

Only the HBM figure is an NVIDIA specification. The other bandwidths are derived from each SM's bytes-per-cycle rate, and the latencies are order-of-magnitude figures from microbenchmarks. Shared memory is the GPU's distinctive level. It is a fast scratchpad the programmer fills explicitly, so a block of threads can reuse data without going back to HBM. Most GPU kernel optimisation is choosing what to put there.

F

How a GPU hides a memory wait

Each SM holds up to 64 resident warps (2048 threads). Every cycle the scheduler picks any warp whose operands are ready. With enough warps in flight the ALUs never idle, so the chip needs no branch predictor or out-of-order engine.

The trick only works when a kernel has far more threads than the chip has lanes. A kernel with 1000 threads leaves an H100 almost empty. Registers also cap residency. 2048 threads sharing 65536 registers get 32 each, so a kernel that needs 64 per thread halves the warps the SM can hold.

G

Graphics pipeline and compute pipeline

The vertex and fragment stages run as ordinary warps on the same SMs. Only the rasteriser, the render output units (ROPs) and the texture units are fixed-function. CUDA and OpenCL skip the fixed stages and hand you the SMs directly. On RTX gaming cards, ray-tracing cores are a third fixed-function block that walks bounding-volume trees and tests ray-triangle hits. The H100 has none, and no display outputs: it is a compute part.

H

Why matrix multiply is the GPU's home turf

Multiplying two n×n matrices takes 2n3 FLOPs and moves 3n2 numbers. Arithmetic intensity grows with n:

I=2n33n2⋅4 bytes=n6 FLOP per byte

The roofline model says a kernel is memory-bound when its intensity is below the machine's ratio of peak FLOPS to bandwidth.

Machine Peak FP32 Bandwidth Ridge point
H100 SXM 67 TFLOPS 3.35 TB/s 20 FLOP per byte
H100 tensor BF16 989 TFLOPS 3.35 TB/s 295 FLOP per byte
EPYC 9654 about 7 TFLOPS 461 GB/s 15 FLOP per byte

A 4096-wide matmul has intensity near 680 FLOP per byte, so it saturates even the tensor cores. A vector add has intensity 0.08 and is memory-bound on everything. Tensor cores exist because large dense matmul is the one workload that can keep 989 TFLOPS fed. It is also the inner loop of every neural network.
